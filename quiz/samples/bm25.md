## Answer

`build_index` makes one pass over the corpus: a `Counter` of each document's tokens, and postings that map each term to a list of `(doc_id, tf)` in ascending doc id. At build time I also precompute the Lucene IDF, ln(1 + (N - n + 0.5) / (n + 0.5)), and each document's length norm, k1 * (1 - b + b * |d| / avgdl), so a query only adds the tf part.

`search` loops over the set of query tokens and reads only those terms' postings, so a document that shares no query term is never scored. Top-k is `heapq.nsmallest` keyed on (-score, doc_id), which gives the lower-id tie-break.

A query that went wrong: "gas price forecast". Second place was a short Brazil currency forecast, em-11168. "forecast" is rare, IDF about 4.4, while "gas" and "price" are common, about 2.2, and tf saturates, so one rare-term match in a short email beat emails that were really about gas prices. Two more: for "california power crisis", three forwarded copies of the same Chronicle article took three of the top five, because nothing detects near-duplicates; and for "larchfield audit" only em-12167 mentions Larchfield, so ranks two to five are unrelated short audit emails, because BM25 always fills k and has no relevance cutoff.

Fixes I would make: deduplicate by body or thread, drop results far below the top score, and add phrase or proximity matching. The same index backs `search_emails`, built lazily once under a lock, and memory recall uses the same code.
