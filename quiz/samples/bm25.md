## Answer

**Short answer:** one pass builds postings plus precomputed IDF and length norms, a query scores only the documents in its own terms' postings, and I can name three queries it got wrong and why.

#### Index · `bm25.py:26-48`
- One pass over the corpus: a `Counter` of each document's tokens
- Postings: term → list of `(doc_id, tf)`, in ascending doc id
- Precomputed at build: Lucene IDF `ln(1 + (N - n + 0.5) / (n + 0.5))` and each document's length norm `k1 * (1 - b + b * |d| / avgdl)`
- So a query only adds the tf part

#### Search · `bm25.py:51-70`
- Loops over the **set** of query tokens and reads only those terms' postings: a document sharing no query term is never scored
- Top-k is `heapq.nsmallest` keyed on `(-score, doc_id)` → lower id wins ties (`bm25.py:69`)

#### Queries that went wrong
- **"gas price forecast"**: second place was a short Brazil currency forecast, em-11168. "forecast" is rare (IDF ≈ 4.4), "gas" and "price" common (≈ 2.2), and tf saturates, so one rare-term match in a short email beat emails really about gas prices
- **"california power crisis"**: three forwarded copies of the same Chronicle article took three of the top five; nothing detects near-duplicates
- **"larchfield audit"**: only em-12167 mentions Larchfield, so ranks 2–5 are unrelated short audit emails; BM25 always fills k and has no relevance cutoff

#### Fixes I would make
- Deduplicate by body or thread
- Drop results far below the top score
- Add phrase or proximity matching

- The same index backs `search_emails`, built lazily once under a lock
- Memory recall uses the same code
